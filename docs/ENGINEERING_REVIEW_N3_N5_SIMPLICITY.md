# N3–N5 合并前审查：冗余、复杂度与实际需求

日期：2026-10-07。审查范围：`main@a38406f` 到 `6499f6f`，对应 PR #29–#32；同时追踪相关既有调用方。当前结论为代码审查及一个真实浏览器定向复现，未重新执行 Windows/native 流程。初次审查只记录发现。用户随后授权“修复后合并”，本文件末尾追加实际修订与验收记录。

## 结论

整体没有失控的过度工程化。关闭句柄、异步结果的所有者检查、同步操作门禁和流式归档都对应已经存在的行为或资源问题；新增模块都有实际调用方。文件数增加主要来自明确职责拆分和回归，不应把文件数当作复杂度指标。

但不能直接按“所有检查通过”结束评审：N5a 存在真实输入回归；导入 Worker 的运行时预算记账也比当前执行模型需要的复杂。N4 搬迁了既有查询实现，尚未消除其中重复读取与双向依赖。建议先修复 F1，再做小范围减法。

## F1 / P2：裁切每次输入重建 Worker，并禁用正在输入的表单

位置：`studio/src/ImportGenerated.tsx:43` 的 effect、`:107` 的坐标输入、`:127` 的 fieldset；`studio/src/assets/importTasks.ts:46` 的整图解码。

每次坐标 `onChange` 都改变 `regionKey`，触发 `setSprite(null)`、`setLoading(true)`、新 Worker、文件读取、完整 PNG 解码及 alpha 扫描。`loading` 随后禁用包括当前坐标框在内的整个 fieldset，导致焦点丢失。素材文件本身没有改变，这里把轻量输入和昂贵的素材重检绑在了一起。

真实 Chromium 复现，复用现有 `StudioUi` 的 React 页面和纯 Python fixture：

1. 导入 2048×2048 的 RGBA PNG，启用源 PNG 裁切。
2. 聚焦“源图左”，全选后以每键 180 ms 输入 `800`。
3. 实际值为 `8`，`document.activeElement` 已不是输入框；本次输入创建一个新导入 Worker，页面无 JS 错误。

原回归 `test_studio_ui.py:447` 使用 `fill(value)` 一次性替换值，再等待处理完成，所以没有覆盖逐键输入。此前 10 项 UI 通过不能证明这段输入交互正确。

同一路径的关闭、取消及 Escape 在 `loading` 时全部不可用（`:118`、`:125`、`:152`）。底层已有 abort/terminate，但正常用户无法在素材检查中主动取消；既有“三次导入/取消”UI 用例是在检查完成后才取消。这个限制原本就存在，N5a 的可取消 Worker 尚未改善它。

最小修正方向：坐标输入在编辑期间保持可用，把昂贵检查安排在输入确认/失焦时，保留当前素材 URL 和最后有效预览；结果只能对应已检查的坐标。尚未检查的值不得用于预检提交。素材检查期间允许关闭，通过已有 cleanup 终止 Worker；提交中的写操作继续保持原门禁。先采用这个局部方案，不为每次输入增加长期 raster 缓存或任务调度器。

验收：逐键输入 `800` 后得到 `800`；编辑过程不中断焦点；未确认坐标不重复解码；结果迟到不授权新坐标；检查中取消后 Worker/URL 释放且不能重新发布。

## F2 / P3：一次性导入任务使用了无额外约束作用的运行时预算租约

位置：`studio/src/assets/importTasks.ts:23`，以及 `studio/tests/artwork.test.mjs:383`。

生产调用每个 Worker 仅执行一个任务，无缓存、无排队，也不共享 `MemoryBudget`。当前文件上限为 16 MiB、像素上限为 16,777,216，因此两条路径的最大记账值分别为：

- inspect/mask：48 + 320 + 0.5 = **368.5 MiB**；
- prepare：48 + 256 + 0.5 = **304.5 MiB**。

两者始终低于固定的 384 MiB 预算。所有满足现有文件/像素限制的生产任务都会通过这层记账；预算拒绝测试是通过注入生产未使用的 64 MiB 配置触发的。租约释放也不等于实际像素缓冲立即回收，当前真正结束任务资源的是 Worker 终止。

这是局部机制冗余，并非整个 `MemoryBudget` 都应删除。美术渲染 Worker 具有真实缓存、pin/evict 和多个资源竞争，仍需要它。建议仅简化一次性导入路径：保留文件/像素检查和资源估算说明，用边界测试核对上限，去掉没有生产竞争关系的租约及测试专用预算注入。384 MiB 也不能解释为浏览器或 GPU 总内存上限。

## N4 的边界仍不完全单向，但不应为形式完整继续拆层

`workspace_query.snapshot` 调用 `issues.model_issues`，后者又从 `workspace_query` 取得模型匹配及 Overlay 工具；`poses.update_poses` 调用 snapshot，而 snapshot 调用 poses 的读取函数。函数内 import 使其能够正常运行，但模块间仍是双向关系。

这不构成运行故障，也不是本轮新增的虚构需求。N4 已解决纯查询必须经过 studio 编排入口的问题；它没有完成全部领域模块解耦。下一次实际修改失败证据时，可传入本次已计算的证据，减少反向读取。当前不单独创建一组接口或服务来追求依赖图形式上的整齐。

## 应保留的必要复杂度

| 机制 | 对应的真实约束 | 判断 |
| --- | --- | --- |
| `DraftBridge` 关闭终态 | 外部 Agent 会保留旧入口，异步操作可能迟到 | 保留；关闭与 revision CAS 处理不同问题 |
| `ArtworkClient` Worker 身份检查 | 崩溃/替换后的旧回调可能影响新实例 | 保留 |
| `WorkspaceOperations` 当前所有者 | React busy 更新不是同步互斥，旧 finally 不能释放新操作 | 保留；43 行局部实现规模合适 |
| 保存启动后再同步 block | 先 block 会拒绝保存，等保存结束再 block 会留下插入窗口 | 保留当前顺序，改善可读性即可 |
| `saved` 与编辑草稿分离 | 用户编辑、保存基线和 Agent token 必须分别表达 | 保留，不属于同一数据的无意义复制 |
| store/query 与 studio 兼容入口 | 纯用例独立测试，已有 native/CLI 调用仍存在 | 保留，不急于删除兼容入口 |
| ZIP 分块哈希、容量/路径校验 | 真实归档体积、跨 Windows 路径及可重新导入约束 | 保留；标准库即可满足 |

没有发现这些新增公开抽象完全没有生产调用。少量 `try/finally`、`isCurrent` 和几行 Base64 转换的重复，尚不值得再抽取一套通用异步执行框架。当前主要问题是导入的执行时机和多余记账，而不是缺少更多架构层。
