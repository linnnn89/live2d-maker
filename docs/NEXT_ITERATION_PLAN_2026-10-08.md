# 上游方案复评与后续迭代计划

日期：2026-10-08。代码基线：`main@b56e2d656b1107ea805c1082cfe31b43e3696753`，包含已合并的 Windows W1 / PR #33；本轮 fetch 后没有更新提交。

输入是用户提供的[上游研究原文](research/UPSTREAM_RESEARCH_2026-10-08.md)，已原样归档。方案复评阶段对照了下列关键实现及 Windows 记录，并复读 Krita 的 `jobs.py`；没有重新验证原文全部上游、Star、模型效果或性能，没有运行 Windows/native/GPU 测试。第1–7节为计划与设计，后续实际进展追加在第8节。

## 1. 判断与近期目标

研究的总体方向成立：借用局部素材、可重复比较和少量编辑提示，改善现有 Cubism 建模结果。需要调整的是实施顺序，以及把“缺能力”与“已有能力尚未用好”分开。

**下一轮目标：让用户或 Agent 提供的一张单眼闭眼 PNG，经过现有导入、语义设置和原生重建，得到可检查、可恢复的闭眼效果。** 先做一个原创最小样例，再用已有角色验证。它是功能验证样例，不开启逐类制作完整角色素材的任务。

紧接着只改这个流程暴露的主要问题：定位不准才考虑 landmark 提示，形变不对才修局部 keyform，网格有缺口才改网格。若现有流程已经可用，就完成操作说明和必要的入口改进，不强行新增底层能力。

近期顺序：**Q1 小范围修正 QA 假设 → V1 单眼闭眼变体 → 根据结果选一个改进方向。** 原方案把 landmark 接入放在变体前，容易先承担坐标、签名和原生绑定改动，却还不知道它是否是主要瓶颈。

成功标准是：能完成上述编辑、比改前更符合期望、需要的人工修正更少；保存/重新打开后结果可重现。测试数量、候选仓库数量和新增模块数量不作为收益指标。

## 4. 近期实施计划

### Q1：让现有 QA 适用于实际模型与最小样例

**解决的问题**：不带头发参数的样例不能运行 Studio QA，模型参数范围与固定取值可能不一致，单参数通过也不能说明转头时闭眼正常。这些问题直接阻碍 V1，不另设长期“质量平台”项目。

实施内容：

1. 从 `qa_workspace` 提取小型纯函数，根据当前构建报告的参数列表生成 spec。保留既有 `qa.py` 渲染、截图、联系表和报告路径；不添加插件机制或规则 DSL。
2. 转角等端点来自实际 min/max/default；闭眼、张嘴等动作只对已知语义、有效取值生成。不能把任意参数的 min 都命名为“闭眼”。缺少头发只记为不适用，不阻断眼睛样例。
3. 保留原有可用检查，增加直接相关的转头＋闭眼、X/Y 组合。对相同参数状态去重，使用少量明确组合，不做所有参数的笛卡尔积。用户显式提供的未知/越界参数仍报错，不悄悄删除或夹到合法范围。
4. 报告写清已覆盖动作和不适用项；只有 neutral 的模型只能算加载/渲染检查。沿用“已渲染，视觉结果需检查”的边界，不把截图成功改称美术质量通过。
5. 准备两个范围明确的用例：可再生成的原创单眼/无头发素材与已有 ds 角色。原创小样例可入仓；真实角色的大型产物继续留在本地证据目录。

**验收**：无头发、单侧眼睛、非默认参数范围均能生成合法且可解释的 spec；组合只使用存在的参数；明确错误输入仍失败。PC 上真实 Cubism 能完成两类样例的对应渲染，并由人查看眼部裁图与组合姿态。

**实施边界**：云端可完成纯 Python spec 逻辑及有意义的单元用例，不改 native 构建/绑定代码。真实调用接线和渲染结果在 PC 验收；若接线必须启动 Windows 链才能判断，就将接线留在同一阶段的 PC 部分，不凭 mock 宣称完成。

**停止点**：Q1 能支撑 V1 即结束。固定时间步序列可在 V1 需要检查眨眼过渡时接现有 `viewer.reset/step`，不先开发录制平台。Golden 差图仅在同后端、版本、镜位、时间状态下比较；首轮由人审查，不引入统一像素阈值拦截正常的美术修改。

### V1：用现有能力完成单眼闭眼变体

**交付行为**：用户或 Agent 提供一张透明闭眼 PNG → 预览放置和 mask → 确认导入 → 指定 `EYE_CLOSE` 与明确左右侧 → 保存并完整重建 → 检查睁眼、半闭、闭眼及转头组合 → 接受或恢复。

实施内容：

1. 先使用人工绘制 PNG，或外部工具已生成的 PNG。不依赖新的 LLM SDK、在线生成服务或自动提示词系统，先判断素材进入模型后是否有用。
2. 先在无 Overlay 的最小样例完成路径，再在真实项目副本上比较。新增图层改变拓扑时按现有规则完整重建；旧 Overlay 不兼容则保留旧成功版本并明确处理新基线，不能自动丢弃编辑或放宽兼容检查。
3. 复用现有导入预检、保护 mask、来源信息和语义 override。检查现有操作是否能表达整个流程；只有出现具体阻碍才补入口或定向修正，不新增“变体库”领域模型。
4. 对比 EyeOpen 的 1 / 0.5 / 0：原睫毛是否形成双线，眼白/虹膜是否漏出，绘制闭眼线是否错位，左右眼是否串联，转头后是否仍对齐。`EYE_CLOSE` 的透明度已有实现，但这些组合效果需要 PC 实测。
5. 记录完成一次修正所需操作、耗时和残留缺陷，用相同姿态的改前/改后裁图判断收益。若现有通路足够，交付操作说明和样例即可，不为产生代码提交而重写它。

**验收**：源美术在保护 mask 外零差；参数驱动的眼部效果经过真实渲染与人工确认；保存/重开结果一致；失败保留旧成功模型。mask 外零差针对素材导入，不要求角色转头后的整张渲染图在 mask 外不动。

**Agent 时序**：候选属于启动时的目标部件、图像和 revision A。用户编辑产生 B 后，旧结果不能自动 apply，也不能仅换成 B 的 token 冒充重新评估；复用已有版本检查和准备/提交语义。允许重新读取 B、重新检查候选，形成新的提案。首轮只需一个候选的预览/采纳，不增加常驻生成任务或多候选缓存。

**实施边界**：云端可改纯前端入口、说明和独立的素材/版本逻辑；原生眼睛通道、遮罩、关键形与实际重建留到 Windows 修改和验证。若已有路径成功，不预先改 Kotlin。

**停止点**：单眼样例和真实项目确认收益后，关闭本阶段。嘴形、双眼、发根、颈部及整角色自动生成不是顺延的必做清单。

## 5. V1 之后根据什么选择下一步

完成 Q1/V1 后只选择主要瓶颈对应的一项。没有出现相应问题的项维持待评估，不并行铺开全部架构。

### L1：只有自动定位不准，才接入少量 landmark 构建提示

适用证据：正确的素材和语义仍反复因眼角/闭眼线等位置推断偏差而需要手调。先确定原生算法真正需要的一组点，不先定义覆盖眼嘴头发颈部的通用骨架协议。

最小设计：

- 坐标继续存于美术 IR；构建设置明确启用哪些已确认的点，默认关闭。设置只引用部件/点，不再复制一份坐标。已有任意注记不能升级后自动改变绑定。
- [binding.py](../tools/authoring_rig/binding.py) 在稳定 part ID → source layer ID 映射处适配提示；复用 native 现有坐标变换。明确原图左上原点、像素单位、Y 方向及角色左右，避免第二套世界坐标。
- 仅实际被算法消费的点与启用设置进入模型输入签名，并贯通 stale、构建复用、QA 和 Overlay 基线。修改生效点应使 base rig 及下游失效，不要求重新栅格化 PSD；无关注记保持原有注记行为。
- 未启用时保留现有自动结果；明确启用但缺点/非法时给出具体输入错误，不静默切回另一种算法。用户关闭提示才能回到自动模式。

验收应比较开启/关闭效果，并检查移动生效点确实触发重建、修改无关注记不重建、旧结果不能误判为当前结果。签名兼容策略与实际接线一起完成，不能只加一个暂时没人消费的字段。原生接入在 Windows 完成。

这里的美术 landmark 与已有素材配准 anchors、`RigGeometryTools` 的局部位移 landmarks 用途不同；可复用计算，不能因为名称相似而直接混用契约。

### K1：位置正确但形变不对，优先做现有关键形的局部修正

先用已有 keyform/warp/`fit_local`、Overlay/Journal 和眼部裁图，修正一个明确姿态。目标图先作为对照与人工对应点来源，不先训练拟合器或引入优化框架。

只有这条路径确实操作繁琐，才借用 nijigenerate 的目标图/镜像/路径交互。所有输出必须能表达为当前 Cubism 导出支持的编辑；在转头组合中检查父级变形，不只检查部件局部坐标。不能把“局部修正可以改善”扩大为全自动目标图拟合的承诺。

### M1：出现细结构缺损时，才开展网格专项

先把实际缺陷缩减为可重复输入，必要时补细发丝、孔洞饰物、近接分离岛、薄缝、共线边界这五类小素材。复用现有诊断，比较覆盖面积、孔洞保持、错误连通、有限坐标和索引有效性。

CDT 可作离线对照，不成为运行时前置依赖；有效剖分不唯一，不能用三角索引不同判失败。闭眼或隐藏部件的预期压扁也不能一律判失败。只修改被失败样例定位的算法分支；不扩展为泛用网格框架或全产物逐字节确定性项目。

### T1：贴图画质成为瓶颈时，改善已有超分

原生已有超分配置、缓存、图集重排、桌面入口与测试；Studio 当前构建设置尚未暴露这项能力。先看用户是否需要从 Studio 调用，以及现有 2x/4x 的实际收益，再决定接入入口。

修正原方案中“锁定 UV 和图集布局”的表述：

- 若原位替换等尺寸贴图，保持 UV 和图集布局是合理约束。
- 现有超分路径会重打图集，UV 数值和图集位置可以改变；必须验证映射回原图层像素后仍然对齐，图集/UV/页面引用同步更新。`TextureUpscaleTest` 已验证这种映射关系以及顶点、三角与部分 CMO3 往返性质。
- 若声称“只提升贴图”，还要针对实际改动确认绑定、关键形和变形器行为没有变化；顶点数量相同不足以证明兼容。不能因此绕过现有 Overlay 基线限制。

真实 nunif 集成在 W1 因未配置而跳过，后续若选择此方向再在 PC 验证画质、耗时和峰值显存。当前不新增超分后端，也不设计热替换贴图协议。

### G1：实际推理或拆图失败再决定模型侧工作

See-through 先在固定输入、模型、分辨率下测一次完整推理的耗时/峰值显存，区分编码器、主模型和解码阶段，再决定缓存或卸载；不承诺未经测量的节省比例。

Qwen 只在现有拆图无法处理的真实输入上对比，评价“后续需要补多少眼白/睫毛等部件”，不只看分层图是否好看。输出继续使用现有 IR 和导入检查。Bunraku 等可复现代码和具体收益出现后再评估。

## 6. 架构、时序与内存约束

保留当前职责：美术 IR 保存素材/几何/语义，Python 负责工作区与构建编排，Kotlin 负责原生绑定，Overlay/Journal 保存模型编辑，Cubism 负责实际预览。已有清晰边界足以承载近期工作；不因上游用了队列、节点图或新格式就引入同类抽象。

| 实际场景 | 继续采用的处理 | 本轮不增加的机制 |
|---|---|---|
| A 启动计算，用户编辑为 B，A 结果迟到 | 检查当前修订/目标身份；拒绝旧提案，重新读取和评估 | 自动 rebase、最后写入覆盖、多套 token |
| 关闭或切换工程后旧结果返回 | 沿用终态/所有权检查与资源释放；新增入口接入同一生命周期 | 通用任务总线或跨工程结果自动转投 |
| 计算已取消但底层还返回结果 | 结果不能发布；临时 bitmap/URL/文件由当前所有者清理 | 为单次导入再引入预算租约或常驻对象池 |
| 原生重建/Overlay 应用失败 | 保留旧成功产物；展示失败原因，按既有规则恢复 | 静默降级、自动丢 Overlay、偷偷放宽拓扑校验 |

不要从“Worker/URL 计数为零”推断 GPU 已释放，W1 已证明 canvas bitmap 可能独立存活；同样，不因这种已修复的问题重做所有缓存。新功能若增加候选图或预览，只管理其实际新增的资源，并针对打开/取消/关闭测量趋势。不先扩充全局内存管理器，不设未经设备测量的普遍显存阈值。

完整 MCP 网络迟到交错仍是已知验证缺口；涉及 MCP/窗口生命周期改动时，在 PC 补这一条实际路径。近期不改这些路径时，不为穷举所有交错引入新状态机。
